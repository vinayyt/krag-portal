# ADR 002 — Internationalisation Strategy

**Date:** 2025-01-15
**Status:** Accepted

## Context

The portal serves Norwegian buyers (default `nb-NO`) with English as a secondary locale. Copy must be maintainable by non-developers (content editors), and locale switching must not cause full page reloads.

## Decision

### Routing
- URL-based locale prefix: `/nb/...` and `/en/...`
- `localePrefix: "always"` ensures locale is always explicit and SEO-friendly
- Default locale `nb` — Norwegian Bokmål

### Message catalogs
- Single JSON file per locale: `messages/nb.json`, `messages/en.json`
- Namespace keys match screen names: `landing`, `auth`, `questionnaire`, `overview`, etc.
- Bilingual data (project names, phase names, etc.) stored as `BiString = { no, en }` and resolved at render time with `pick(obj, locale)`

### Type safety
- `useTranslations(namespace)` from next-intl is typed via `messages/nb.json` as the reference type
- `BiString` type is used for all database strings that appear in the UI

### Number/date formatting
- Numbers: `Intl.NumberFormat("nb-NO")` for kr, `Intl.NumberFormat("en-US")` for NOK
- Dates: `Intl.DateTimeFormat` with locale; booking slots use `fmtWeekday/fmtDay/fmtMonth`

## Consequences

- Adding a new UI string requires updating both `nb.json` and `en.json` — a lint rule should catch missing keys in CI
- Database content (project descriptions, phase names) is always bilingual — single-language content is not supported
- The `pick()` helper must be used consistently; hardcoded Norwegian strings in components are a bug
